## 3. Product Intent

### Approved Inventory

Admin/review users need a safe internal view of all items that have reached APPROVED_FOR_INTERNAL_USE status. This inventory:

- Shows internally approved candidates with safe metadata
- Supports filtering by target type
- Provides readiness summary and safe next-action hints
- Is internal-only — does not imply publication, export, or delivery
- Does not create public URLs, signed URLs, or CDN endpoints
- Does not expose provider, storage, or binary details

### Internal Revision Request

After inspecting an approved or reviewable item, an admin/reviewer may decide the content needs further work. The internal revision request:

- Is a **controlled, auditable action** — not a generic status update
- Requires a safe reason/message from the actor
- Does not auto-trigger generation or regeneration
- Does not approve, publish, or export anything
- Does not expose provider/storage details
- Preserves the existing FP-012 review audit trail

## 7. Internal Revision Request Concept

### Purpose

A reviewer/admin can request internal revision for a review target. This is a **narrow, auditable action** that signals that an approved or reviewable item needs further work.

### Candidate Behavior by Source State

| Source State | Revision Request Behavior | Rationale |
|-------------|--------------------------|-----------|
| **APPROVED_FOR_INTERNAL_USE** | Move to CHANGES_REQUESTED with audit trail | Safe — existing state; reviewer wants changes after internal approval |
| **IN_REVIEW** | Existing REQUEST_CHANGES action covers this | No new action needed |
| **NEEDS_REVIEW** | Existing REQUEST_CHANGES action covers this | No new action needed |
| **CHANGES_REQUESTED** | Append safe note (idempotent) | Already in changes-requested state; avoid duplicate transitions |
| **REJECTED** | Not allowed — must RETURN_TO_DRAFT first | Rejected items need explicit return-to-draft before new changes |
| **DRAFT** | Not applicable — not yet in review | Cannot request revision on a draft |
| **AI_GENERATED** | Not applicable — not yet submitted | Cannot request revision before review submission |

### Design Decision: Reuse vs. New Action

**Recommended approach: New narrow action `REQUEST_INTERNAL_REVISION`**

Rationale:
- `REQUEST_CHANGES` from FP-012 is designed for reviewer→creator feedback during active review
- `REQUEST_INTERNAL_REVISION` has different semantics: admin/reviewer requests re-examination of an *already approved* item
- The transition APPROVED_FOR_INTERNAL_USE → CHANGES_REQUESTED via `REQUEST_INTERNAL_REVISION` is a distinct audit event
- For CHANGES_REQUESTED source state, the action appends a safe note instead of a redundant transition
- This keeps the action taxonomy explicit and auditable without becoming a generic status update

### Properties

| Property | Requirement |
|----------|------------|
| Requires safe reason/message | ✅ Yes |
| Auditable | ✅ Yes — creates audit trail entry |
| Generic status update | ❌ No — narrow action with defined source states |
| Auto-triggers generation | ❌ No |
| Approves anything | ❌ No |
| Publishes anything | ❌ No |
| Exposes provider/storage | ❌ No |

## 8. Domain Model Direction

### Reuse of ReviewApplicationService

The internal revision request should be implemented as a new action within the existing `ReviewApplicationService` action model:

```
ReviewApplicationService.requestInternalRevision(request)
```

This follows the same pattern as `requestChanges()`, `approveForInternalUse()`, etc.:
- Receives a typed request DTO
- Validates source state
- Performs state transition via ReviewDomainService
- Creates audit entry
- Returns safe response DTO

### State Transition

```
APPROVED_FOR_INTERNAL_USE → CHANGES_REQUESTED (via REQUEST_INTERNAL_REVISION)
CHANGES_REQUESTED → CHANGES_REQUESTED (no-op transition, append note only)
```

All other source states → rejected with safe error response.

### Actor Role Constraints

| Actor Role | Can Request Internal Revision? |
|------------|-------------------------------|
| REVIEWER | ✅ Yes |
| ADMIN | ✅ Yes |
| CREATOR | ❌ No — creators use existing SUBMIT_FOR_REVIEW flow |
| SYSTEM | ❌ No — system cannot request revision |

### Existing Constraints Preserved

- SYSTEM cannot approve
- CREATOR cannot approve
- `actorRole` request field is NOT authentication — production auth integration remains deferred
- No new review states added — uses existing CHANGES_REQUESTED
